# Phoenix CI & Validation Pipeline

## 1. Overview & System Role

In the Phoenix self-healing architecture:
* **Phoenix Agent**: Handles runtime monitoring of containers, streaming logs, and detecting crashes.
* **LLM Reasoning Layer**: Analyzes stack traces and failure evidence to generate proposed patches.
* **Docker Sandbox**: Performs immediate, ephemeral validation of candidate patches.
* **GitHub Actions (`Phoenix CI`)**: Serves as the **authoritative CI and code-quality gatekeeper** for developer pushes, Pull Requests, and Phoenix-generated fix branches (`phoenix/fix/*`).

```
Developer Push / Phoenix Fix Branch
               │
               ▼
   ┌──────────────────────┐
   │  GitHub Actions CI   │
   └──────────┬───────────┘
              │
   ┌──────────┴──────────┐
   ▼                     ▼
[PASSED]              [FAILED]
   │                     │
   │                     ▼
   │           Produce Structured Report
   │           • phoenix-ci-report.json
   │           • Pytest XML / logs
   │           • Container logs
   │                     │
   ▼                     ▼
Ready for PR /     Phoenix Ingests Evidence
Merge Sign-Off     For AI Root-Cause Analysis
```

## 2. Workflow Triggers & Permissions

The workflow is configured in [`.github/workflows/phoenix-ci.yml`](../.github/workflows/phoenix-ci.yml).

### Triggers
1. **Push events** to:
   - `main`: Core production line.
   - `dashwanth15`: Active feature branch.
   - `phoenix/**`: Autonomous fix branches generated by Phoenix (e.g., `phoenix/fix/incident-001`).
2. **Pull Request events** targeting `main` or `dashwanth15`.
3. **`workflow_dispatch`**: Manual or API-triggered runs.

### Security & Permissions
- Follows the principle of least privilege:
  ```yaml
  permissions:
    contents: read
  ```
- **Zero hardcoded secrets**: No API keys, passwords, or credentials are baked into the pipeline.

## 3. Pipeline Stages

The workflow executes sequentially on `ubuntu-latest`:

| Step | Action | Tool / Command | Failure Behavior |
| :--- | :--- | :--- | :--- |
| **1. Checkout** | Fetches repository tree | `actions/checkout@v4` | Halts job |
| **2. Python Setup** | Sets Python 3.11 with pip cache | `actions/setup-python@v5` | Halts job |
| **3. Install Deps** | Installs application & dev dependencies | `pip install -r requirements-dev.txt` | Halts job |
| **4. Lint & Static** | Verifies code formatting and syntax | `flake8 sample-app --config=.flake8` | Marks step failed, generates log |
| **5. Pytest** | Runs automated test suite | `pytest --junitxml=... -v` | Marks step failed, records XML |
| **6. Docker Build** | Builds application container | `docker build -t phoenix-sample-app:ci ./sample-app` | Marks step failed, records log |
| **7. Health Check** | Runs container & polls `/health` | `curl -f http://localhost:8080/health` (15 retries) | Marks step failed, dumps logs |
| **8. Teardown** | Collects container logs & removes container | `docker logs`, `docker rm -f` | Runs `always()` |
| **9. Report Gen** | Synthesizes structured JSON & Step Summary | Built-in shell generator | Runs `always()` |
| **10. Artifact Upload** | Preserves all reports and logs for Phoenix | `actions/upload-artifact@v4` (14 days) | Runs `always()` |
| **11. Final Assertion** | Verifies all required stages succeeded | Exit code assertion | Fails workflow if any stage failed |

## 4. Structured Report: `phoenix-ci-report.json`

On every run (pass or fail), Step 9 generates `ci-reports/phoenix-ci-report.json`:

```json
{
  "status": "success",
  "commit_sha": "b82849a62629b319ff92e10a202dfa640103bbda",
  "branch": "dashwanth15",
  "workflow": "Phoenix CI",
  "run_id": 1827491023,
  "run_number": 12,
  "event_name": "push",
  "repository": "Rudranshhhhh/Phoenix-Self-Healing-Software-System",
  "actor": "Dashwanth15",
  "failed_step": "none",
  "exit_code": 0,
  "error_summary": "All checks passed successfully.",
  "test_results": "4 passed in 0.89s",
  "timestamp": "2026-10-03T10:55:00Z"
}
```

### In Case of Failure
When a test or step fails, `status` becomes `"failed"`, `failed_step` points to the exact stage (e.g. `"pytest"` or `"docker_run_health"`), `exit_code` is `1`, and `error_summary` provides the context.

## 5. Artifacts Produced

The following files are preserved in the `phoenix-ci-report-<sha>` artifact bundle:
1. `phoenix-ci-report.json`: Machine-readable summary for Phoenix.
2. `pytest-results.xml`: Standard JUnit test report.
3. `pytest-output.log`: Full terminal output from the test runner.
4. `flake8-report.txt`: Linter output.
5. `docker-build.log`: Docker build transcript.
6. `health-response.json`: Payload returned by `/health`.
7. `container.log` / `container-failure.log`: Container runtime stdout/stderr.

## 6. How Phoenix Consumes CI Results

### A. Consuming via GitHub API (Recommended for Agent / Backend)
Phoenix can fetch the latest run artifacts for any commit or fix branch:
```bash
# 1. List workflow runs for the fix branch
GET /repos/{owner}/{repo}/actions/runs?branch=phoenix/fix/incident-001

# 2. List artifacts for the run
GET /repos/{owner}/{repo}/actions/runs/{run_id}/artifacts

# 3. Download the artifact zip containing phoenix-ci-report.json
GET /repos/{owner}/{repo}/actions/artifacts/{artifact_id}/zip
```

### B. Future Direct Webhook Endpoint (Recommended Spec)
When the Phoenix backend adds direct CI ingestion, the following route can receive CI results:

* **Endpoint**: `POST /api/ci/runs`
* **Request Body**:
  ```json
  {
    "incident_id": "optional-incident-uuid",
    "ci_report": {
      "status": "failed",
      "commit_sha": "...",
      "branch": "phoenix/fix/incident-001",
      "failed_step": "pytest",
      "exit_code": 1,
      "error_summary": "AssertionError in test_health_endpoint_healthy",
      "test_results": "1 failed, 3 passed"
    }
  }
  ```

## 7. Local Developer Verification Commands

Before pushing, developers can run the exact CI steps locally:

```bash
# 1. Install dev requirements
pip install -r requirements-dev.txt

# 2. Run linter
flake8 sample-app --config=.flake8

# 3. Run automated tests
pytest -v

# 4. Build Docker container
docker build -t phoenix-sample-app:test ./sample-app

# 5. Run and health check container
docker run -d --name phoenix-sample-app-test -p 8080:8080 -e PORT=8080 phoenix-sample-app:test
curl -f http://localhost:8080/health
docker rm -f phoenix-sample-app-test
```
